## 2. 总体结论

两树文案底子好于预期：**「很抱歉/似乎/为您/作为AI助手/智能/赋能」类 AI 味禁词在四层全部零命中**；系统提示词多为合格电报式（EXTRACT_SYSTEM、INTENT_SYSTEM、popup 系列可作格式基线）。差距集中在五类：

1. **标点与格式不统一**（约 55 处）：省略号「…/...」并存、半角/全角冒号并存、范围符四种写法（`1~365`/`1～10`/`1-100`/`2~32`）、句末句号时有时无；
2. **术语漂移**（约 20 组）：同一概念多种说法，见 §3 总表；最严重的是**同名工具描述在 tool-registry.js 与 agent-task-service.js 双份维护且已分叉**（与 12/14 号审阅的「两套注册表」P0 同根）；
3. **中英混排无空格 / 内部黑话外露**（约 30 处）：「unknown计划」「状态110」「安全正整数」「落盘」「失败关闭」「有头」「降级」「Server Edge」「wechatcli」；
4. **整句英文残留**（约 14 处）：集中在 rolling 发布/迁移类 CLI 的抛错与 usage 尾注——恰是运营发布时最先看到的文字；
5. **错误/通知缺要素**（约 34 处）：只报「发生了什么」不给「怎么办」；通知以「请及时处理」收尾无入口无动作；价格提醒缺价格数字。

## 4. 文案风格规范（后续新增文案的验收基线）

1. **句式**：短句、动宾开头；禁「请站在/请以…视角」角色扮演客套，改「以…视角分析：A、B、C」。
2. **禁词表（AI 味）**：很抱歉、似乎、好像、为您（贴心服务）、亲爱的用户、智能、赋能、助力、轻松、一键、AI 正在分析——静态闸门词表见 §6 Batch 5。
3. **错误提示三要素**：`{对象}{动作}失败：{原因}。{下一步}`；禁以「是否可达」「稍后重试」「请及时处理」空泛收尾。
4. **确认对话框模板**：`确认{动词}{对象}？{后果一句}`；动词统一「确认」不用「确定」；后果用「不可恢复/不可撤销」；结尾「是否继续？」而非口语「确定继续吗？」。
5. **空态模板**：`暂无{对象}` + 一句下一步动作（动词开头）；禁只写「暂无数据」或设备语气「就绪」。
6. **状态文案不带行动指令**：chip/状态列只写状态（「结果未知」），指令放 Notice 或按钮旁。
7. **按钮动宾化**：名词式/缩写按钮改「动词+对象」；二字极限词（查询/刷新/保存/取消）可保留。
8. **标点**：人读消息全角冒号「：」、全角括号、省略号统一「…」、范围符统一全角「～」；单句短提示（≤15 字）不加句号，多句才句号收尾。
9. **数字与英文排版**：英文词、阿拉伯数字与中文之间加半角空格（`近 7 天`、`最多 50 项`）；英文单位译为中文（s→秒）。
10. **机器标识外露格式**：`中文描述（CODE）`，标识不放句首；枚举允许值超过 5 个时禁全量 dump 进 message，给「见文档/--help」。
11. **权限提示**：一律 403 + `仅管理员可{动词}` 或 `{动作}需要{中文名}权限（capability.key）`；禁止用参数校验错误（400）表达权限。
12. **通知三段式**：首行「结论（含对象）」→「店铺/日期/关键数字」→「下一步：动作+入口」；涉金额/价格/阈值必须带数字。
13. **工具 description 单一来源**：tool-registry.js 与 agent-task-service.js 同名工具描述逐字一致（从 ALL_TOOLS 派生，随 12/14 号审阅 Batch 3 的注册表收敛一并根治）。
14. **校验失败句式**：`{字段}{约束}（收到「{值}」）`，需动作时追加「，请{动作}」。
15. **删系统视角与自我解释**：「已加入队列」「暂时无法形成结论」「为避免死循环」「这是一条通知测试消息」类只留结论。
