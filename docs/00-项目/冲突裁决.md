# 冲突裁决

## 知识库目录

- 主题：项目知识放在哪一层
- 来源 A：YT-ANSE 知识模型建议 `ontology/`、`glossary/`、`product/`、`adr/`、`state/` 等目录
- 来源 B：本次指定的整理技能要求 `00-项目/` 到 `99-归档/` 的生命周期分层
- 选定权威：整理技能的生命周期分层
- 决定：canonical 知识留在 `docs/` 的生命周期目录。准则快照不改写
- 理由：用户指定按该技能改造本仓库。快照是锁定镜像，改它会破坏 tree 一致性
- 后续门禁：刷新准则快照时另记 ADR，不把快照目录改成产品知识的第二入口

## OrchDesk 基线提交

- 主题：`dsh-v0.1.3-alpha.1` / `d347e703908d0406b7a7ef80e3a0e594d86b2215` 能否当作已核对锁定点
- 来源 A：2026-09-29 研究笔记引用本地 `dsh.lock` 和一份决策文档，写成当前基线
- 来源 B：同日 GitHub `commits` 接口返回 422，tag `dsh-v0.1.3-alpha.1` 返回 404，公开 tag 列表没有 `dsh-*`，本地对象库也没有该提交
- 选定权威：可解析的 Git 对象
- 决定：不把该提交或 tag 写成已核对锁定点。插件证据点仍是 [来源并入](来源并入.md) 中的 `b68a955776dffd5fe45e3e0e2ca075d2b297ee65`
- 理由：不能用当时的笔记补一个现在解析不到的 tree
- 后续门禁：若要恢复这个基线名，必须重新解析到 commit 和 tree，并记 ADR

## OrchDesk 检出是否前移

- 主题：整理日本地 OrchDesk HEAD 是否替换证据点
- 来源 A：文档记录的证据检出 `b68a955776dffd5fe45e3e0e2ca075d2b297ee65`
- 来源 B：整理日本地 `main` 为 `e29881bb6d2ab751549fc2d3f335a5339e747a83`，且前者是后者的祖先
- 选定权威：仍用 `b68a955776dffd5fe45e3e0e2ca075d2b297ee65` 作为插件删除决定的证据点
- 决定：不把未经重新核对的新 HEAD 写成插件清单的证据
- 理由：祖先关系只证明历史连续，不证明九个插件的装载表没有变化
- 后续门禁：改接前若证据点要前移，先重读 `apps/desktop/dsh-runtime.ts` 并记 ADR

## 聚合门禁 `pnpm run verify` 该不该当验收

- 主题：`verify` 链的地位。README 写过「不要用 `pnpm run verify` 当验收」，[检查点](检查点.md) 各轮也写「未用 pnpm run verify」
- 来源 A：链里挂着四个根门禁（`verify-plugins` / `intent-gate-verify` / `verify-orchestration` / `verify-trace-upload`），它们装载删除清单上的九插件，本仓库没有 `@deepseek-ai/cordis`，四条必崩在 require
- 来源 B：[SPEC](../30-开发/替换契约.md) 的删除清单与 [ADR 0005](../70-决策/0005-进程内嵌入与插件删除.md) 决定九插件删除且不迁移；A 组门禁核对的行为在本仓库已不存在
- 选定权威：SPEC 的删除清单
- 决定：从链路移除并删除这 6 个文件（含 `verify-p5.mjs`、`prepare-trace.cjs`）。`pnpm run verify` 从 2026-10-01 起就是可运行的聚合门禁：版本守卫 + `apps/desktop` 的 30 个套件
- 理由：README 那句告诫的真正原因是 A 组门禁必然崩，而不是「验证本身不该做」。移除死门禁后，那句话的前提消失；留着它会让下一轮继续绕开聚合门
- 后续门禁：链中任何一步红，就按 [代码审阅（2026-10-01）](../40-质量/代码审阅-2026-10-01.md) 的恢复入口定位，不得再用「单跑几个脚本」代替聚合门

## 版本号记在哪一页

- 主题：应用版本与发布层的关系
- 来源 A：[发布状态](../50-发布/发布状态.md) 写「没有产品发布。没有版本号……」
- 来源 B：`apps/desktop/package.json` 带着从精简版继承来的 `0.16.2`，版本守卫要求文档与它对齐，而它核对的 `docs/00-项目/CHECKPOINT.md` 已在文档整合中改名且不记版本
- 选定权威：两边都要，但各管一件事 —— `package.json` 是机器版本号的源，发布页只说「有没有发布过安装包」
- 决定：版本行落在根 `README.md`（`当前版本：v0.16.2`），守卫只核对这一处。`docs/50-发布/发布状态.md` 继续说没有发布，不改写
- 理由：「未发布」不等于「没有包版本」；把两者混为一谈会让守卫要么核对不存在的文件、要么被迫声称已发布
- 后续门禁：递增版本时必须同步 README 那一行，否则 `verify` / `build` / `dist` 在第 2 步红

- 主题：2026-10-01 出现的 `docs/40-质量/YTPX/YTPX-Skill-v1.1/`（24 个文件：SKILL、SPEC×5、RULES×5、SCHEMAS×3、TOKENS、CHECKLIST×3、ANTI-PATTERNS、REVIEW）。它是设计评审方法论，不是 stepcode 的产品需求，却落进了规范性知识库层

- 来源 B：该包已被本项目的界面审阅与优化动作实际使用，删掉会丢掉可追溯的工作方法
- 选定权威：唯一入口 + 分层职责，但保留内容
- 决定：包留在 `docs/40-质量/YTPX/` 作为记录位置，不改名为 `guidelines/`（那会破坏快照的 tree 一致性）。补齐 11 个缺失的 frontmatter，并在 [知识库入口](../README.md) 挂一条索引，写明它是方法论而非产品需求。`status: draft`、`source: YTPX-Skill-v1.1` 标出来，免得被当成 canonical 契约引用

- 后续门禁：若要把方法论升级为 stepcode 的规范，必须逐文件改 `status` 并在 SPEC 里建立引用；若决定移出 `docs/`，走一条 ADR，不要直接删
