# ADR 0009 — 官方 CLI 是可更新的核，桌面壳单独更新

- 状态：已接受
- 日期：2026-10-03
- 取代：[ADR 0008](0008-跟随-step-code-源仓库.md) 第 5 条（安装包不能当运行时），以及其中「壳不把安装目录当作运行时」。
- 不改：[ADR 0004](0004-gui-两档.md) 的两档文案。危险命令仍由本界面确认。

## 背景

用户要求官方 CLI 成为 StepCode Desktop 的核，并且可以 OTA；桌面壳自己也要能 OTA。

核对结果：

- 官方安装包没有 `createStepExtensionInline`。`step update` 只替换 `step.exe` 和它旁边的资源，不会改 `resources/step/index.js`。
- 已安装的 `step.exe` 认 `--sdk-stdio`。2026-10-03 对本机 `0.1.1` 的握手成功：`initialize` 有响应，`query.start` 被接受。
- 桌面壳的 electron-updater 指向 `ra1nzzz/stepcode`，但不自动下载、不自动安装。通道上还没有可装的 release 时，检查可以失败，不能装另一个产品。

## 决策

1. 找到独立的 `step` / `step.exe` 时，用户回合由这份二进制执行。包内 `resources/step/index.js` 只在找不到 CLI 时兜底。CLI 开了回合却失败时，不偷偷换回包内核。
2. CLI 更新只运行这份二进制的 `update`。桌面壳自己的文件名不能走这条命令。
3. 没有 CLI 时，用户确认后才从 `https://static-openapi.stepfun.com/stepcode` 下载对应平台包，校验 sha256，装到 `~/.stepcode/bin`。不执行远程安装脚本。
4. 驱动协议固定带权限回调。本 GUI 回答 `permission.request`。拒绝、超时、没有窗口，都是否认。不发送跳过审批的模式。
5. 桌面壳更新仍指向本仓库的 GitHub release。不自动下载，不自动安装。用户点安装之后才下载，并且只在已打包的安装版里替换自身。开发模式拒绝安装。

## 后果

- 官方 CLI 的工具策略随 `step update` 变化。本 GUI 仍拦截协议送回来的确认请求。
- 包内核不跟随 CLI 版本。它只是没装 CLI 时的退路。
- 桌面壳 OTA 要等本仓库发出带 `latest.yml` 的 release。没有 release 时，按钮只能报告没有可装的包。
