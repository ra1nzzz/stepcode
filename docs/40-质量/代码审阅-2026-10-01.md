- 也先查了「会不会连测试一起删掉守卫」：`e2e-fix-verify.cjs` 确有 withhold 断言，但它测的是**渲染层**发前高风险提示（`#outboundWarn`，页内自己的分类器），与主进程这道门无关；其注释引用的 `packages/plugin/compensation/lib` 在本仓库根本不存在。所以移除不动任何被断言的行为

- 钉住：`arch-guard` 新增 R19，断言 `main.ts` / `tool-exec.ts` 里既取不到 `getService('compensation')` 也不得再出现 `outboundGate`，并带正控（两文件必须仍有 `approvalGate`，否则规则只是在扫空集）。编号让开 R13——它已被「导入未接线」占用。双向验证：把 `getService("compensation")` 塞回 `main.ts` → **28 通过 1 失败**；撤掉 → **29 通过 0 失败**

## 第八轮（同日，确认门不再对死窗等 120 秒）

`main.ts` 的 `rendererWindow()` 在拿不到主窗时兜底返回「任意活着的窗」。这个兜底给通知类通道是有意的（主窗重建后不断流），但它同时供给了危险命令确认门的 `hasWindow`：悬浮窗与内置浏览器窗都没有 preload，收不到 `orchdesk:approval-request`，于是 `hasWindow()` 为真、弹窗发给死窗，确认要等满 `APPROVAL_TIMEOUT_MS`（120 秒）才被超时兜底拒绝。方向是 fail-closed，代价是主进程带着一条不动的回合挂两分钟。`notifyToolStep` 的注释里已经记过一次同形态的「发给死窗」缺陷。

## 第九轮（同日，发布路径不再被软链绕过）

`publishSkill` 的白名单用 `path.resolve` 判前缀，而 **`resolve` 不解析符号链接**：`skills/evil.skill` 只要是指向 `~/.ssh/id_rsa`（或任何本机文件）的软链，前缀检查照样通过，随后的 `readFileSync` 跟着链接读出去——把任意文件上传到技能市场。它同时还有个不一致：校验的是 `resolved`，读的却是入参原路径。

- 修法：白名单开在 `fs.realpathSync` 之后（skills 目录与文件都取真身），并且**读的就是那个已验证的真身**；skills 目录不存在、文件不可解析各自给明确原因，不混成一句
- 用例（`guanji-verify.cjs` 第 8 项，子进程探针 + electron 桩，因为 `setToken` 要 `safeStorage`）：软链发布必须被拒，且拒绝原因必须来自路径判定而不是网络层（这条反向断言正是为了区分旧实现——旧实现会一路放行到上传）；真身在 skills 内的普通 `.skill` 不得被误杀；本机建不出软链时打 NOTE 而不是假装跑过
- 双向验证：改回 `path.resolve` 口径 → **7 通过 1 失败**；恢复 realpath → **8 通过 0 失败**

## 第十三轮（同日，界面不再宣称主进程不提供的行为）

两条如实记在这：

1. **stdin 监听未被证明。** 删掉两处 `child.stdin.on('error')` 后用例仍绿：Windows 上向已关闭的管道读端写入得到的是静默 EOF，而不是 POSIX 那样的 EPIPE `'error'` 事件，本机构造不出可观测的异步 error。监听器按 Node 语义与 `terminal-pty.ts:321` 已经写下的同一条规矩保留，属防御性修复。要判红得能在客户端内部替换 `spawn`；`dist/mcp-client.js` 是 ESM 静态 import，本机没有可用的 mock 缝。用例名已改成它实际断言的内容，不再自称反证
2. **`encryptKey` 返回空串那条守卫今天到不了。** `credentials.encryptSecret` 是纯 node:crypto 的 AES-256-GCM，除空输入外不会返回空串，所以 `models-save` 里的「key 落不下就报失败」在当前平台是死分支。它挡的是「将来主密钥来源换成 safeStorage 或平台 keystore 后静默丢 key」，与 `PRD NFR` 的「凭据必须加密」一致。没有为它编造用例

变异前后实测：`credentials-verify.cjs` 45 通过 0 失败（原 40）；`mcp-client-verify.cjs` 12 通过 0 失败（原 10）。数字为本轮实跑。
