## 变异验证（双向判据）

新增守卫不做「函数存在」式断言：先把守卫改回旧行为，必须有用例判红，才算验证。改动从 `HEAD` 恢复，用例落在 `credentials-verify.cjs` 的 B2 组与 `mcp-client-verify.cjs` 的 A/B 组。

| 守卫 | 用例 | 改回旧行为后 | 结论 |
|---|---|---|---|
| `models-save` 拒绝重复提供商 id | 重复 id 判失败，且磁盘上提供商数量仍是 2（拒绝要真的没写） | 判红 | 检出 |
| `models-save` 拒绝空 / 纯空白 id | 空白 id 判失败并报原因 | 判红 | 检出 |
| `models.json` 读坏时中止保存 | 保存判失败，且损坏原文逐字节留在盘上（旧实现写成空 providers） | 判红 | 检出 |
| MCP 参数先判上限再取值 | 400 个参数判失败并报「参数过多」 | 判红 | 检出 |
| stdin `'error'` 监听 | 「子进程先退出时干净失败且不崩」 | **仍为绿** | **变异存活** |
| 无加密后端时报保存失败 | 无 | 未测 | 见下 |

两条如实记在这：

1. **stdin 监听未被证明。** 删掉两处 `child.stdin.on('error')` 后用例仍绿：Windows 上向已关闭的管道读端写入得到的是静默 EOF，而不是 POSIX 那样的 EPIPE `'error'` 事件，本机构造不出可观测的异步 error。监听器按 Node 语义与 `terminal-pty.ts:321` 已经写下的同一条规矩保留，属防御性修复。要判红得能在客户端内部替换 `spawn`；`dist/mcp-client.js` 是 ESM 静态 import，本机没有可用的 mock 缝。用例名已改成它实际断言的内容，不再自称反证
2. **`encryptKey` 返回空串那条守卫今天到不了。** `credentials.encryptSecret` 是纯 node:crypto 的 AES-256-GCM，除空输入外不会返回空串，所以 `models-save` 里的「key 落不下就报失败」在当前平台是死分支。它挡的是「将来主密钥来源换成 safeStorage 或平台 keystore 后静默丢 key」，与 `PRD NFR` 的「凭据必须加密」一致。没有为它编造用例

变异前后实测：`credentials-verify.cjs` 45 通过 0 失败（原 40）；`mcp-client-verify.cjs` 12 通过 0 失败（原 10）。数字为本轮实跑。
