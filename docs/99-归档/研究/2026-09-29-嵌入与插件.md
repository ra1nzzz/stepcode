# 嵌入方式与插件去留核对

- 访问日期：2026-09-29
- 上游：https://github.com/stepfun-ai/Step-Code
- 观察点：`main` @ `93ebc5bea25032a77af007a968a8998b492989f5`（当天 `commits/main` 仍是这个提交）
- 宿主：`ra1nzzz/orchdesk` 检出 `b68a955776dffd5fe45e3e0e2ca075d2b297ee65`
- 结论：进程内按官方 CLI 的同一接缝组合库。不把 `--sdk-stdio` 或 `--mode rpc` 当作本 GUI 的权限面。九个 Cordis 插件随 `dsh-runtime` 删除，能力不迁入这次替换。

## 库的形态

`packages/coding-agent/package.json`：

- 包名 `@step-harness/coding-agent`，版本 `0.84.4`，`"private": true`，`"type": "module"`，许可 MIT
- `engines.node` 为 `>=22.19.0`
- 唯一导出子路径是 `"."` → `./dist/index.js`
- `bin.step` 指向 `dist/bundle/step.js`。发行二进制另由 bun compile 产出，不是这个导出
- `@step-harness/config` 是 `workspace:*`。依赖里还有 `@silvia-odwyer/photon-node` 和 quickjs

因此不能 `npm install` 一个已发布的嵌入 SDK。进程内使用等于把锁定点的 workspace 编进宿主。

同一观察点的 `packages/coding-agent/src/index.ts` 确实导出编程接口，包括 `createStepCode`、`createStepAgentSession`、`createStepExtensionInline`、`StepStdioHost`、`RpcClient`、`decideStepToolCall`、`STEP_PERMISSION_PRESETS`。有导出不等于有一条已发布、可单独升级的库契约。

## 三条接缝，不是一条

| 接缝 | 核对到的行为 | 对本 GUI 的含义 |
|---|---|---|
| CLI 组合根 | `apps/cli/src/bootstrap/extensions.ts` 把 `permission` 传给 `createStepExtensionInline`。`apps/cli/src/ui/runtime/approval.ts` 的 `createApprovalProvider` 只提供 `confirm`，注释写明它通向 `permissions.ts` | 这是两档预设和危险命令确认的接缝 |
| `createStepCode` / `createStepAgentSession` | `stepcode-runtime.ts` 的门面不安装权限控制器。`step/sdk.ts` 写明自己不包含运行时行为，只装饰设置和会话存储 | 单独调用它们得不到 `bypass` / `autopilot` |
| `--sdk-stdio` | `StepStdioHost` 的 `permissionMode` 只接受 `default`、`acceptEdits`、`plan`、`bypassPermissions`、`dontAsk`。`bypassPermissions` 跳过 SDK 审批回调。`sandbox.enabled` 直接报 `SANDBOX_UNAVAILABLE` | 这是另一套宿主词，不是 CLI 预设 |
| `--mode rpc` | `rpc-types.ts` 的命令有 prompt、模型、会话、bash，以及 `extension_ui_request` 的 `confirm`。没有设置 `bypass` 或 `autopilot` 的命令。`rpc-mode.ts` 未检索到 permission / preset / `decideStepToolCall` | 不能把它当成两档的控制面 |

CLI 参数（`packages/coding-agent/src/cli/args.ts`）没有名为 `bypass` 或 `autopilot` 的旗标：

- `--approval-mode` 只接受 `confirm`、`auto`、`strict`
- `--non-interactive-approval` 只接受 `allow`、`deny`
- `STEP_AUTOPILOT` 只打开有界的模型错误后续跑

`permissions.ts` 的 `resolveStepPermissionPresetWithProvenance` 能在启动时折预设。未另给 `approvalMode` 时，`STEP_PERMISSION_PRESET` 可以是 `bypass` 或 `autopilot`。若给了 `approvalMode` 或 `STEP_APPROVAL_MODE`，则 `auto` 且 `STEP_AUTOPILOT` 为真、并且非交互审批不是 `deny` 时得到 `autopilot`，否则 `auto` 得到 `bypass`。`normalizeStepPermissionMode` 另把 `default` / `acceptEdits` 折成 `confirm`，`plan` 折成 `strict`，`bypassPermissions` 折成 `auto`。`dontAsk` 不在这个函数里。

这不能当成子进程方案已经成立。同一文件的 `handleToolCall` 在 `context.hasUI` 为假时，危险命令直接阻断，不调用 `confirm`。`bypass` 和 `autopilot` 预设自己的 `nonInteractiveApproval` 都是 `allow`，但注释写明危险命令在没有界面时仍然失败关闭。子进程若没有把 `ui.confirm` 交回本 GUI，两档都会把危险命令变成拒绝，而不是确认。

`--non-interactive-approval allow` 只放行普通确认，不放行危险命令，也不能代替 GUI 确认。`--non-interactive-approval deny` 还会让上面的折算从 `autopilot` 掉回 `bypass`。

`StepStdioHost` 的构造选项写了嵌入或单测时可省略 `onExitRequested`。这只说明该类可以被放进进程，不说明要用它的 `permissionMode` 替换 `decideStepToolCall`。

## 优劣

进程内库组合：

- 能沿用 CLI 已经在用的 `permission` + `confirm` 接缝，两档仍是 `bypass` 和 `autopilot`
- 危险命令确认留在 `decideStepToolCall`，不经过 `bypassPermissions`
- 代价：私有 ESM、Node `>=22.19.0`、workspace 依赖、photon / quickjs，并且工具进程和 Electron 主进程同生共死
- 跟随官方更新仍是移动锁定点，不是 `step update`。这与 ADR 0003 已经接受的更新方式一致

子进程：

- 隔离崩溃域，也不受 Electron 自带 Node 版本约束
- 发行物更接近「官方 CLI 二进制」
- 现有两条宿主协议都没有核对到「GUI 分别设置 `bypass` / `autopilot`，并把危险命令确认交回 GUI」
- 启动参数可以折出预设，但无界面时危险命令被拒绝，不是被本 GUI 确认
- `--sdk-stdio` 的 `bypassPermissions` 会跳过 SDK 审批回调。`permissions.ts` 把同一个词折成 `auto`，host 门却不调用那个函数。两处语义不同，都不能映射成完全信任

OrchDesk 桌面壳是 Electron `^36.0.0`。文档里出现过 `process.versions.electron=36.9.5`。本增量没有核对这个 Electron 自带的 Node 是否满足 `>=22.19.0`。这是实现前的前置条件。不满足时升壳的运行时，不改走 `--sdk-stdio`。

## OrchDesk 插件

`apps/desktop/dsh-runtime.ts` 在 Electron 主进程里 `new Context()`，然后装载宿主服务和 9 个插件。不是先拉起一个 dsh 子进程。`PLUGIN_NAMES` 为 `intent`、`trace`、`authz`、`brain`、`multi`、`memory`、`prompt`、`compensation`、`evolution`。

宿主服务 `host-services.ts` 提供 `sandboxPolicy`、`approval`、`agents`。授权档是 `default`、`trusted`、`paranoid`。这三档不是 Step Code 的预设。

| 插件 | 核对到的耦合 | 桌面侧调用 | 处置 |
|---|---|---|---|
| intent | `@deepseek-ai/dsh-agent`、`dsh-session`。运行时注释：无 provide，监听 `agent/pre-step` | `agent-turn.ts` 调用 `firePreStep` | 随 dsh 删除。不迁。工具裁决只留 `decideStepToolCall` |
| trace | 同上，无 provide | 装载时注入 `trace.json` 和内置上报令牌 | 随 dsh 删除。不迁。上报不是替换核的条件 |
| authz | `inject = ['sandboxPolicy', 'approval']`，`ctx.provide('authz')` | 宿主回灌 `authz-grants.json` | 随 dsh 删除。不迁。它保存的是 OrchDesk 三档，不是两档预设 |
| brain | `inject = ['agents']`，依赖 `dsh-agent`、`dsh-session` | 运行时注释写明桌面专家团不走这里 | 随 dsh 删除。不迁 |
| multi | `inject = ['agents']`，依赖 `dsh-agent`、`dsh-session` | `ipc-plugins.ts` 的 `composeTeam`，preload 与渲染层有入口 | 随 dsh 删除。不迁。专家团依赖 `ctx.agents` |
| memory | 依赖 `dsh-agent`、`dsh-session`，`ctx.memory` | preload、`main.ts` 的摘要回调、宿主四域落盘 | 随 dsh 删除。不迁。本增量不把旧 JSON 读入新核 |
| prompt | 源码检索只见到 Cordis 和 schemastery，没有 dsh-agent。`ctx.promptLib` | `agent-turn.ts`、`ipc-prompt.ts`、preload | 随 dsh 删除。不迁。不注入 dsh 类型，但只由 dsh 装载器装上。不为它保留 Cordis |
| compensation | `inject = ['approval', 'sandboxPolicy']`，依赖 dsh-agent / dsh-session | preload、`main.ts`、`ipc-plugins.ts` | 随 dsh 删除。不迁。它按 OrchDesk 授权档做外发确认，会变成第二套审批 |
| evolution | 同上 | preload、`ipc-plugins.ts`。临时插件只在内存 | 随 dsh 删除。不迁。临时插件是 Cordis 能力 |

市场插件不是第 10 个内置名，但 `setMarketPluginEnabled` 同样把产物 `ctx.plugin` 到这个 Context 上。装载器随 `dsh-runtime` 删除。本增量没有逐个清点市场目录，也不把它们迁入 Step Code。

`sandboxPolicy` 的模式是 `read-only`、`workspace-write`、`danger-full-access`。Step 的 stdio host 对 `sandbox.enabled` 返回不可用。这次替换不迁移这套沙箱策略，也不打开那个不可用开关。
