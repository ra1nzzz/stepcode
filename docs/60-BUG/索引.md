## 活跃缺陷

- **BUG-032 快照顺序把全量复制放到启动路径上**（P2，未修，等并行会话让开 `ipc-data-ops.ts`）。`snapshotData` 原先因 `fs.cpSync` 目标在源内而每次抛错，等于从未备份；修好复制之后，`checkForUpdates`（`boot-desktop` 启动约 8 秒无条件调用）会在主线程同步拷整个数据目录。正解：先探到更新、再备份

- **BUG-033 沙箱日志的「外发」档已无生产者**（P2，未修，属并行会话的文件）。第十轮删掉 `outboundGate` 时，唯一的 `recordSandbox({ kind: 'outbound' })` 一起没了，而 `sandbox-log.ts:26` 的 `SandboxKind` 仍含 `'outbound'`、`renderer/app.js` 仍提供该筛选项与「外发」标签。实测本机持久日志里没有任何 `outbound` 条目，且本仓库从未发布过构建（[发布状态](../50-发布/发布状态.md)），所以也不存在「历史条目还要能筛」的兼容理由——这一档在 UI 里永远为空，等于宣称一道已不存在的门。修法：从 `SandboxKind`、筛选项 `:2270` 与标签表 `:253` 三处一并去掉。`renderer/app.js` 正被另一会话改，本轮不与其争同一文件

- **BUG-035 `event-emit` / `event-consumer` 整簇未接线**（P2，未修，需要决定）。`event-emit.ts` 与 `event-consumer/{index,router,sse-consumer,ws-consumer}.ts` 从 `main.ts` 不可达，也没有任何套件加载它们；只有 `event-consumer` 内部三处 `import type { CanonicalEnvelope } from '../event-emit'` 把它们互相连成一个孤岛。`apps/desktop/CHANGELOG.md` 的 `phase8: Canonical event emission + SSE/WS consumer` 说的是这批代码，而知识库（`docs/`）里搜不到任何声称该行为存在的页面。要人裁决：接线（并补 PRD/SPEC 与套件）还是删除（并记一条与 ADR 0005 同式的决定）。现在由 `arch-guard` R24 点名豁免并写明理由，不会再无声扩大。同簇那两个 `.ts` 版测试副本（`event-emit-verify.ts`、`event-emit-quick-verify.ts`）已先行移除：它们不在 verify 链上、用 `node` 直跑必失败（TS 未编译），对后来人是「门禁坏了」的假信号，而 `.cjs` 版本已在链上覆盖同一行为——移除它们不预支上面那个接线/删除的决定

- **BUG-036 反馈与遥测界面向用户承诺了不发生的上报**（P2，未修）。[SPEC](../30-开发/替换契约.md) 的删除清单把 `trace` 判为「删除。不迁」，主进程侧 `getService('trace')` 恒为 null、`orchdesk:trace-feedback` 明确返回 `{ ok:false, unavailable:true }`（同日第十二轮实测）。但 `renderer/app.js` 仍四处按「遥测存在」说话：`:2316` 与 `:2622` 的开关文案「脱敏遥测上报至 **OrchDesk 公开仓库**（仅白名单字段，不含任何消息内容）」指向另一个产品的仓库；`:969` 在用户点过反馈后把该行标成「已记录反馈 · 已脱敏遥测」；`:129` 还把 TRACE 当作可用插件卡片列出（带 caps 与「脱敏：开」的配置项）。同一文件 `:2623-2624` 又写着「已关闭…仅本地缓冲，不上传」「未内置上报凭据（开发模式）」——界面自己前后矛盾。修法二选一，都要人点头：随删除清单把这一整面（开关、文案、插件卡、反馈态措辞）去掉，或统一改口为「未启用」并让开关不可操作（项目既有口径：不可用即不可操作）。文案落在并行会话随时会重写的 `renderer/app.js`，本轮只登记

## 已闭合

- **BUG-036 反馈与遥测界面承诺了不发生的上报**（P2，同日第十三轮修复）。实测确定的事实：`data-action="trace"` 在 `renderer/app.js` 里**没有任何分发分支**，点「有帮助/需改进」不会调 `bridge.traceFeedback`，`state.feedback` 只从持久会话记录回填；`trace` 按 SPEC 删除清单已卸下且不迁移，主进程 `orchdesk:trace-feedback` 恒返回 `unavailable`。修法：撤掉整块反馈控件（含那句不会发生的成功回执文案），把 TRACE 开关的三档文案改成「未启用：trace 随 dsh 卸下且不迁移，本壳不向任何仓库上报」。新增 `arch-guard` R26 禁止界面再宣称这类行为（带正控；植入一句坏文案即判红）
  - **同时撤回我登记时的一处过头说法**：原文写「把 TRACE 当可用插件卡片列出」。实测插件页的徽章与开关走 `state.pluginRuntime`（运行时优先），只有运行时不认识该 id 时才回落到 `PLUGINS` 常量的 `on` 字段；而运行时对九个插件一律报 `available:false`（T4 与 `ipc-guard-verify` 的等待条件都断言过），所以卡片显示的是「未接入」，不是假称可用。`PLUGINS` 里残留的 `on: 1` 与 `PLUGINS.length` 参与的小节计数是另一回事（措辞层面），不是本条缺陷

- **BUG-033 沙箱日志「外发」档无生产者**（P2，同日第十二轮修复）。`outbound` 从 `SandboxKind`、`KINDS` 白名单与渲染层筛选项/标签表一并去掉。测量过才动手：本机两个数据目录里没有任何落盘日志，且本仓库从未发布过构建，所以不存在需要继续可筛的历史条目。修的时候还抓到并行会话的一次漂移——筛选项列表里 `outbound`（0 生产者）留着，而 `browser`（11 生产者）被丢了。新增 `arch-guard` R25 把「联合 / 标签表 / 筛选项 / 生产者」四处口径钉成一致，两个漂移方向都跑过判红

- **BUG-031 观雅集安装审查的信任边界**（P1，同日第十一轮修复）。安装的风险等级现在只认服务端清单：`listSkills()` 顺手把派生结果缓存进 `serverSkills`，`installSkill` 用缓存里的 caps 判风险，入参的 `caps` / `auth` 一概不信；清单里没有该 slug 时按高危处理（必须走确认弹窗），用户显式确认后仍可安装，降级不成死路。用例走**真 HTTP 替身**（`node:http` 起在 127.0.0.1 随机端口），双向伪造都测：服务端说高危而调用方把 `caps` 清空、`auth` 报 0 → 仍 `needs-auth`；服务端说只读而调用方谎报高危 → 不该弹确认，直接走到下载。把 `installSkill` 改回只信入参即判红（8 通过 1 失败）
